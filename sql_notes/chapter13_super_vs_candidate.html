Chapter 13: Super Key vs Candidate Key

📖 Definition

Super Key vs Candidate Key: Database theory-la key concepts understand panna Super Key and Candidate Key romba important. Super Key ennanagra table-la oru or more columns combination which can uniquely identify each record - extra unnecessary columns irundhaalum paravala. Candidate Key ennanagra minimal super key - unnecessary columns remove panni simplest form-la irukura super key.

🏗️ Key Hierarchy

🔴 SUPER KEY
Any unique combination
↓
🟡 CANDIDATE KEY
Minimal super key
↓
🟢 PRIMARY KEY
Chosen candidate key

📊 Comparison Table

Aspect 🔴 Super Key 🟡 Candidate Key

🔍 Key Analysis Process

1Identify All Possible Super Keys

🟡 Candidate Keys Found

Why minimal: Each single column unique-a iruku, so extra columns add panna vendam

2Test Minimality for Candidate Keys
Candidate Key Validation:

{student_id}: ✅ Unique, no subset possible - CANDIDATE KEY
{roll_number}: ✅ Unique, no subset possible - CANDIDATE KEY
{contact_number}: ✅ Unique, no subset possible - CANDIDATE KEY

💡 Complex Example: Employee Projects

-- Employee project assignments CREATE TABLE project_assignments ( employee_code VARCHAR(20) NOT NULL, project_code VARCHAR(20) NOT NULL, assignment_date DATE NOT NULL, role VARCHAR(50) NOT NULL, hours_per_week INT DEFAULT 40, manager_code VARCHAR(20), INDEX idx_emp (employee_code), INDEX idx_project (project_code), INDEX idx_date (assignment_date) ); -- Sample data INSERT INTO project_assignments VALUES ('EMP_001', 'PROJ_A', '2024-01-15', 'Developer', 40, 'MGR_001'), ('EMP_001', 'PROJ_B', '2024-02-01', 'Lead', 30, 'MGR_002'), ('EMP_002', 'PROJ_A', '2024-01-15', 'Tester', 35, 'MGR_001'), ('EMP_002', 'PROJ_C', '2024-03-01', 'Analyst', 40, 'MGR_003'), ('EMP_001', 'PROJ_A', '2024-06-01', 'Senior Dev', 40, 'MGR_001');
3Complex Table Analysis
Testing Single Columns:
employee_code: EMP_001 appears 3 times - NOT UNIQUE
project_code: PROJ_A appears 3 times - NOT UNIQUE
assignment_date: 2024-01-15 appears 2 times - NOT UNIQUE
role: Not unique across all records - NOT UNIQUE

Testing Two Column Combinations:
{employee_code, project_code}: (EMP_001, PROJ_A) appears 2 times - NOT UNIQUE
{employee_code, assignment_date}: (EMP_001, 2024-01-15) appears 1 time - UNIQUE but not sufficient

Testing Three Column Combinations:
{employee_code, project_code, assignment_date}: All combinations unique - CANDIDATE KEY!
-- Apply the candidate key as primary key CREATE TABLE project_assignments_final ( employee_code VARCHAR(20) NOT NULL, project_code VARCHAR(20) NOT NULL, assignment_date DATE NOT NULL, role VARCHAR(50) NOT NULL, hours_per_week INT DEFAULT 40, manager_code VARCHAR(20), -- Candidate key becomes primary key PRIMARY KEY (employee_code, project_code, assignment_date), INDEX idx_manager (manager_code), INDEX idx_role (role) );

🎯 Practical Decision Making

From Multiple Candidate Keys to Primary Key:

Student table-la 4 candidate keys irundhadhu:

🟡 Candidate Keys:
• {student_id} - System generated, stable
• {roll_number} - Business meaningful
• {contact_number} - Can change
• {user_email} - Can change

🟢 Primary Key Choice: {student_id}
Reason: Stable, integer type (fast), never changes, system controlled
-- Final implementation with proper constraints CREATE TABLE students_final ( student_id INT AUTO_INCREMENT PRIMARY KEY, -- Chosen from candidate keys roll_number VARCHAR(20) UNIQUE NOT NULL, -- Alternative key student_name VARCHAR(100) NOT NULL, course VARCHAR(50) NOT NULL, year_of_admission INT NOT NULL, contact_number VARCHAR(15) UNIQUE, -- Alternative key user_email VARCHAR(100) UNIQUE, -- Alternative key -- Constraints CONSTRAINT chk_year CHECK (year_of_admission >= 2020), CONSTRAINT chk_course CHECK (course IN ('Computer Science', 'Information Technology', 'Electronics', 'Mechanical', 'Civil')), -- Additional indexes INDEX idx_course (course), INDEX idx_year (year_of_admission), INDEX idx_name (student_name) );

❌ Confusing Super Key with Candidate Key: Super key-la redundant columns irukalaam, candidate key-la irukaakoodadhu
❌ Not Testing All Combinations: Systematic-a ella combinations test panna venum
❌ Ignoring Business Logic: Technical uniqueness mattum illa, business sense um irukanum
❌ Choosing Wrong Primary Key: Candidate keys-la irundhu performance and stability consider panna venum
❌ Missing Composite Keys: Single column unique illa-na multiple columns combination try pannunga

💡 Advanced Example: Multi-Branch Banking

-- Bank account transactions across multiple branches CREATE TABLE account_transactions ( transaction_id BIGINT AUTO_INCREMENT, account_number VARCHAR(20) NOT NULL, branch_code VARCHAR(10) NOT NULL, transaction_date DATE NOT NULL, transaction_time TIME NOT NULL, transaction_type ENUM('Deposit', 'Withdrawal', 'Transfer') NOT NULL, amount DECIMAL(15,2) NOT NULL, balance_after DECIMAL(15,2) NOT NULL, teller_id VARCHAR(20), INDEX idx_account (account_number), INDEX idx_branch (branch_code), INDEX idx_date (transaction_date) );
Complex Analysis:

Super Keys Include:
• {transaction_id} - Auto-generated unique
• {account_number, transaction_date, transaction_time} - Account + exact timestamp
• {branch_code, transaction_date, transaction_time, teller_id} - Branch + time + teller
• {transaction_id, account_number} - ID + account (redundant)
• Many other combinations...

Candidate Keys:
• {transaction_id} - Minimal, system generated
• {account_number, transaction_date, transaction_time} - Minimal business key

Primary Key Choice: {transaction_id}
Reason: Performance, simplicity, guaranteed uniqueness
-- Final table with proper key selection CREATE TABLE account_transactions_final ( transaction_id BIGINT AUTO_INCREMENT PRIMARY KEY, -- Chosen candidate key account_number VARCHAR(20) NOT NULL, branch_code VARCHAR(10) NOT NULL, transaction_date DATE NOT NULL, transaction_time TIME NOT NULL, transaction_type ENUM('Deposit', 'Withdrawal', 'Transfer') NOT NULL, amount DECIMAL(15,2) NOT NULL, balance_after DECIMAL(15,2) NOT NULL, teller_id VARCHAR(20), created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP, -- Alternative candidate key as unique constraint UNIQUE KEY uk_account_datetime (account_number, transaction_date, transaction_time), -- Performance indexes INDEX idx_account_date (account_number, transaction_date), INDEX idx_branch_date (branch_code, transaction_date), INDEX idx_type_amount (transaction_type, amount), -- Constraints CONSTRAINT chk_amount CHECK (amount > 0), CONSTRAINT chk_balance CHECK (balance_after >= 0) );

🎯 Key Selection Guidelines

Primary Key Selection from Candidate Keys:

🏆 Preference Order:

1 Stability: Never changing values preferred
2 Simplicity: Single column better than composite
3 Performance: Integer/numeric keys faster than text
4 Size: Smaller keys save storage and improve performance
5 Business Meaning: Meaningful keys user-friendly

📚 Quick Reference

  • Super Key: Any unique combination (can have redundant columns)
  • Candidate Key: Minimal super key (no redundant columns)
  • Primary Key: Chosen candidate key for table
  • Alternate Key: Non-chosen candidate keys (UNIQUE constraints)
  • Analysis Method: Test all combinations, find minimal ones
  • Selection Criteria: Stability > Performance > Simplicity > Business Meaning
