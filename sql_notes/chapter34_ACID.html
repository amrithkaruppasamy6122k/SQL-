ACID Properties Definition (Vilakkam)

ACID Properties: Database transactions la data integrity and reliability maintain panna follow panna veenda 4 fundamental principles. Banking, e-commerce, financial systems pola critical applications la ACID compliance mandatory aagum.

ACID Acronym:
• Atomicity - All or Nothing principle
• Consistency - Data integrity rules follow aaganum
• Isolation - Concurrent transactions interfere panna koodathu
• Durability - Committed data permanent ah preserve aaganum

Yen ACID Important? Database la data corruption avoid pannuradhu, concurrent users safe ah work pannuradhu, system crash aanalum data safe ah irukuradhu ku ACID properties romba crucial.

ACID Properties Overview

BEGIN

Transaction Start

ACTIVE

Operations Execute

COMMIT

Success State

ROLLBACK

Failure State

Transaction Lifecycle: BEGIN la start aagi, operations execute aagi, success aana COMMIT, failure aana ROLLBACK aagum. ACID properties ellaa stages layum apply aagum.

Flow Chart (Otta Padal)

TRANSACTION FLOW WITH ACID:
START TRANSACTION → ATOMICITY Check → CONSISTENCY Validate → ISOLATION Maintain → Operations Execute → Success? → COMMIT (DURABILITY) / ROLLBACK
ACID VALIDATION PROCESS:
Each Operation → Atomicity Boundary → Consistency Rules Check → Isolation Level Apply → Durability Guarantee → Transaction Complete
FAILURE HANDLING:
Error Detect → Atomicity Rollback → Consistency Restore → Isolation Release → Durability Maintain → Clean State Return

A - Atomicity (All or Nothing Principle)

Atomicity Concept

Atomicity: Transaction la irukka ellaa operations um completely success aaganum illa completely fail aaganum. Partial success allow pannadhu. Itha "All or Nothing" principle nu solluvom.

Example: Bank money transfer la debit and credit rendu operations um success aaganum. Debit mattum success aachu credit fail aana entire transaction rollback aaganum.

Atomicity Example 1: Bank Money Transfer

Scenario:

Ravi account la irundhu Priya account ku 15000 rupees transfer pannurom. Rendu operations um atomic ah nadakkanum.

-- Bank Transfer Transaction CREATE TABLE bank_accounts ( account_number VARCHAR(20) PRIMARY KEY, account_holder VARCHAR(100), balance DECIMAL(12,2), last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP ); INSERT INTO bank_accounts VALUES ('ACC001', 'Ravi Kumar', 50000.00, NOW()), ('ACC002', 'Priya Sharma', 25000.00, NOW());
Success Case - Proper Atomicity:
START TRANSACTION; -- Step 1: Debit from source account UPDATE bank_accounts SET balance = balance - 15000 WHERE account_number = 'ACC001' AND balance >= 15000; -- Check if debit was successful SELECT ROW_COUNT() as rows_affected; -- Step 2: Credit to destination account UPDATE bank_accounts SET balance = balance + 15000 WHERE account_number = 'ACC002'; -- If both operations successful, commit COMMIT; -- Verify final balances SELECT account_number, account_holder, balance FROM bank_accounts WHERE account_number IN ('ACC001', 'ACC002');
START TRANSACTION: Transaction boundary define pannurom
balance >= 15000: Sufficient balance check pannurom
ROW_COUNT(): Debit operation success aagudha nu verify pannurom
COMMIT: Rendu operations um success aana permanent ah save pannurom
Atomicity Success: Either rendu updates um aagum illa rendu layum rollback aagum
Failure Case - Atomicity Violation Prevention:
START TRANSACTION; -- Insufficient balance case UPDATE bank_accounts SET balance = balance - 25000 WHERE account_number = 'ACC001' AND balance >= 25000; -- Check affected rows - will be 0 due to insufficient balance SET @affected_rows = ROW_COUNT(); IF @affected_rows = 0 THEN -- Insufficient balance, rollback entire transaction ROLLBACK; SELECT 'Transaction Failed: Insufficient Balance' as error_message; ELSE -- Credit to destination account UPDATE bank_accounts SET balance = balance + 25000 WHERE account_number = 'ACC002'; COMMIT; SELECT 'Transaction Successful' as success_message; END IF;
Insufficient Balance Check: Debit operation fail aana automatic ah detect pannurom
@affected_rows = 0: Update successful ah illa nu check pannurom
ROLLBACK: Any step fail aana entire transaction undo pannurom
Atomicity Protection: Partial transaction never commit aagaadhu

Atomicity Example 2: E-commerce Order Processing

-- E-commerce Order Atomicity START TRANSACTION; -- Step 1: Create order record INSERT INTO orders (customer_id, order_total, order_status) VALUES (101, 2500.00, 'PROCESSING'); SET @order_id = LAST_INSERT_ID(); -- Step 2: Update inventory UPDATE inventory SET quantity = quantity - 2 WHERE product_id = 'PROD001' AND quantity >= 2; -- Step 3: Create order items INSERT INTO order_items (order_id, product_id, quantity, price) VALUES (@order_id, 'PROD001', 2, 1250.00); -- Step 4: Update customer points UPDATE customers SET loyalty_points = loyalty_points + 25 WHERE customer_id = 101; -- All steps successful, commit the transaction COMMIT;
Multiple Operations: Order create, inventory update, order items, loyalty points
@order_id: Generated order ID use pannurom
quantity >= 2: Stock availability check pannurom
Atomic Guarantee: Any step fail aana complete order process rollback aagum

C - Consistency (Data Integrity Rules)

Consistency Concept

Consistency: Database la define panna rules, constraints, triggers ellaam transaction complete aana pinbu valid state la irukanum. Data integrity maintain aaganum.

Types: Primary key constraints, foreign key constraints, check constraints, business rules ellaam consistency maintain pannurom.

Consistency Example 1: Foreign Key Constraint

-- Customer Orders with Foreign Key Consistency CREATE TABLE customers ( customer_id INT PRIMARY KEY, customer_name VARCHAR(100) NOT NULL, email VARCHAR(100) UNIQUE, phone VARCHAR(15) ); CREATE TABLE orders ( order_id INT PRIMARY KEY AUTO_INCREMENT, customer_id INT, order_date DATE DEFAULT CURRENT_DATE, order_total DECIMAL(10,2) CHECK (order_total > 0), FOREIGN KEY (customer_id) REFERENCES customers(customer_id) ); -- Insert valid customer INSERT INTO customers VALUES (201, 'Arjun Patel', 'arjun.patel@gmail.com', '9876543210');
Consistency Success Case:
START TRANSACTION; -- Valid order - customer exists INSERT INTO orders (customer_id, order_total) VALUES (201, 1500.00); -- Consistency maintained - foreign key valid COMMIT; SELECT 'Order created successfully with consistency maintained' as result;
Consistency Violation Prevention:
START TRANSACTION; -- Try to insert order for non-existent customer -- This will fail due to foreign key constraint INSERT INTO orders (customer_id, order_total) VALUES (999, 2000.00); -- This will cause error: Cannot add or update a child row: -- a foreign key constraint fails -- Transaction automatically rollback aagum ROLLBACK; -- Explicit rollback for safety
Foreign Key Check: Customer 999 exist pannadhu, so consistency violation
Automatic Rollback: Constraint violation la automatic ah rollback aagum
Data Integrity: Invalid data enter panna mudiyaathu
Consistency Maintained: Database valid state la maintain aagum

Consistency Example 2: Business Rule Validation

-- Account Balance Consistency with Business Rules CREATE TABLE accounts ( account_id VARCHAR(20) PRIMARY KEY, account_type ENUM('SAVINGS', 'CURRENT', 'FIXED') NOT NULL, balance DECIMAL(12,2) DEFAULT 0.00, min_balance DECIMAL(10,2) DEFAULT 1000.00, CHECK (balance >= 0), -- Balance should never be negative CHECK ( (account_type = 'SAVINGS' AND balance >= min_balance) OR (account_type = 'CURRENT' AND balance >= 0) OR (account_type = 'FIXED' AND balance >= 25000) ) ); -- Custom validation trigger for complex business rules DELIMITER // CREATE TRIGGER validate_account_balance BEFORE UPDATE ON accounts FOR EACH ROW BEGIN -- Savings account minimum balance check IF NEW.account_type = 'SAVINGS' AND NEW.balance < NEW.min_balance THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Savings account balance below minimum required'; END IF; -- Fixed deposit minimum amount check IF NEW.account_type = 'FIXED' AND NEW.balance < 25000 THEN SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = 'Fixed deposit requires minimum 25000 balance'; END IF; END // DELIMITER ;
CHECK Constraints: Balance negative ah irukka koodathu
Business Rules: Account type based minimum balance rules
Custom Trigger: Complex business logic validation
SIGNAL SQLSTATE: Custom error throw pannurom
Consistency Guarantee: Business rules violate panna transaction fail aagum

I - Isolation (Concurrent Transaction Management)

Isolation Concept

Isolation: Multiple transactions simultaneously execute aagumbodhu, oru transaction la changes vera transaction ku visible aagakoodathu until commit aagum varai. Concurrent access problems avoid pannurom.

Isolation Levels: READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ, SERIALIZABLE nu 4 levels irukku.

Isolation Levels Comparison

Isolation Level Dirty Read Non-Repeatable Read Phantom Read Performance
READ UNCOMMITTED Possible Possible Possible Highest
READ COMMITTED Prevented Possible Possible Good
REPEATABLE READ Prevented Prevented Possible Moderate
SERIALIZABLE Prevented Prevented Prevented Lowest

Isolation Example 1: Dirty Read Prevention

Scenario:

Two transactions simultaneously account balance modify pannurom. Transaction 1 value change pannichu aana commit pannala. Transaction 2 uncommitted value read panna koodathu.

-- Session 1: Transaction A SET TRANSACTION ISOLATION LEVEL READ COMMITTED; START TRANSACTION; UPDATE bank_accounts SET balance = balance + 5000 WHERE account_number = 'ACC001'; -- Transaction A not committed yet -- Balance changed from 50000 to 55000 but not committed SELECT 'Transaction A: Balance updated but not committed' as status;
-- Session 2: Transaction B (Different Connection) SET TRANSACTION ISOLATION LEVEL READ COMMITTED; START TRANSACTION; -- This will read the original committed value (50000) -- Not the uncommitted value (55000) from Transaction A SELECT account_number, balance, 'Original committed value' as note FROM bank_accounts WHERE account_number = 'ACC001'; COMMIT;
READ COMMITTED Level: Committed data mattum read pannalam
Dirty Read Prevention: Uncommitted changes visible aagaadhu
Transaction A: Update pannichu aana commit pannala
Transaction B: Original value thaan read pannuchu
Isolation Success: Uncommitted data interference illa

Isolation Example 2: Phantom Read Prevention

-- SERIALIZABLE Isolation Level Demo -- Session 1: Transaction with Range Query SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; START TRANSACTION; -- Count all accounts with balance > 25000 SELECT COUNT(*) as high_balance_accounts FROM bank_accounts WHERE balance > 25000; -- Result: Let's say 5 accounts
-- Session 2: Try to Insert New High Balance Account (Different Connection) SET TRANSACTION ISOLATION LEVEL SERIALIZABLE; START TRANSACTION; -- This insert will be blocked until Session 1 commits -- Prevents phantom read in Session 1 INSERT INTO bank_accounts VALUES ('ACC003', 'New Customer', 30000.00, NOW()); -- This will wait for Session 1 to complete
SERIALIZABLE Level: Highest isolation level
Range Lock: WHERE balance > 25000 range locked
Phantom Prevention: New records insert panna mudiyaadhu
Session 2 Blocked: Session 1 complete aagum varai wait pannuchu
Consistent Results: Session 1 la same count maintain aagum

Isolation Example 3: Deadlock Detection and Resolution

-- Deadlock Scenario and MySQL Auto-Resolution -- Session 1: START TRANSACTION; UPDATE bank_accounts SET balance = balance + 1000 WHERE account_number = 'ACC001'; -- Lock acquired on ACC001 -- Now trying to lock ACC002 (will wait for Session 2) UPDATE bank_accounts SET balance = balance - 500 WHERE account_number = 'ACC002';
-- Session 2 (Simultaneously): START TRANSACTION; UPDATE bank_accounts SET balance = balance + 2000 WHERE account_number = 'ACC002'; -- Lock acquired on ACC002 -- Now trying to lock ACC001 (will cause deadlock) UPDATE bank_accounts SET balance = balance - 1000 WHERE account_number = 'ACC001'; -- MySQL will detect deadlock and rollback one transaction
Deadlock Situation: Session 1 needs ACC002, Session 2 needs ACC001
Circular Wait: Rendu sessions um wait panni irukum
MySQL Detection: Automatic ah deadlock detect pannuchu
Auto Resolution: One transaction ah rollback pannuchu
Error Message: "Deadlock found when trying to get lock" error varum

D - Durability (Permanent Data Storage)

Durability Concept

Durability: Transaction commit aana pinbu, system crash aanalum power failure aanalum data permanent ah preserve aaganum. Committed changes ellaam persistent storage la safe ah store aaganum.

Implementation: Write-ahead logging, transaction logs, checkpoint mechanisms use panni durability ensure pannurom.

Durability Example 1: Transaction Log Verification

-- Enable MySQL General Log to verify durability SET GLOBAL general_log = 'ON'; SET GLOBAL general_log_file = '/var/log/mysql/transactions.log'; -- Durability Test Transaction START TRANSACTION; INSERT INTO bank_accounts VALUES ('ACC004', 'Durability Test Customer', 10000.00, NOW()); UPDATE bank_accounts SET balance = balance + 1000 WHERE account_number = 'ACC001'; -- Critical: COMMIT ensures durability COMMIT; -- Verify transaction is logged and data persisted SELECT account_number, balance, 'Data committed and durable' as status FROM bank_accounts WHERE account_number IN ('ACC004', 'ACC001');
general_log = 'ON': Transaction logging enable pannurom
COMMIT: Data ah disk ku permanent ah write pannurom
Write-ahead Logging: Commit munnadi log file la write aagum
Crash Recovery: System restart aanalum data available irukum
Durability Guarantee: Committed data never lose aagaadhu

Durability Example 2: Binary Log for Point-in-Time Recovery

Binary Logs: All changes binary format la record aagum

-- Complete Banking System with ACID Compliance CREATE TABLE bank_customers ( customer_id INT PRIMARY KEY, customer_name VARCHAR(100) NOT NULL, kyc_status ENUM('PENDING', 'VERIFIED', 'REJECTED') DEFAULT 'PENDING', created_date DATE DEFAULT CURRENT_DATE ); CREATE TABLE bank_accounts ( account_number VARCHAR(20) PRIMARY KEY, customer_id INT, account_type ENUM('SAVINGS', 'CURRENT', 'FIXED') NOT NULL, balance DECIMAL(15,2) DEFAULT 0.00, min_balance DECIMAL(10,2) DEFAULT 1000.00, daily_limit DECIMAL(12,2) DEFAULT 100000.00, status ENUM('ACTIVE', 'BLOCKED', 'CLOSED') DEFAULT 'ACTIVE', created_date DATE DEFAULT CURRENT_DATE, FOREIGN KEY (customer_id) REFERENCES bank_customers(customer_id), CHECK (balance >= 0), CHECK (daily_limit > 0) ); CREATE TABLE transaction_log ( log_id BIGINT AUTO_INCREMENT PRIMARY KEY, transaction_ref VARCHAR(50) UNIQUE, from_account VARCHAR(20), to_account VARCHAR(20), transaction_type ENUM('DEPOSIT', 'WITHDRAWAL', 'TRANSFER'), amount DECIMAL(15,2), balance_before DECIMAL(15,2), balance_after DECIMAL(15,2), transaction_date TIMESTAMP DEFAULT CURRENT_TIMESTAMP, status ENUM('SUCCESS', 'FAILED', 'PENDING') DEFAULT 'PENDING', failure_reason TEXT, created_by VARCHAR(50) DEFAULT USER() ); CREATE TABLE daily_transaction_limits ( account_number VARCHAR(20), transaction_date DATE, total_debited DECIMAL(15,2) DEFAULT 0.00, transaction_count INT DEFAULT 0, PRIMARY KEY (account_number, transaction_date), FOREIGN KEY (account_number) REFERENCES bank_accounts(account_number) );
Complete Schema: Customers, accounts, transactions, limits ellaam track pannurom
ENUM Constraints: Valid values mattum allow pannurom
CHECK Constraints: Business rules database level la enforce pannurom
Foreign Keys: Data integrity maintain pannurom
Audit Trail: Every transaction log pannurom
-- Comprehensive Money Transfer with Full ACID Compliance DELIMITER // CREATE PROCEDURE CompleteMoneyTransfer( IN p_from_account VARCHAR(20), IN p_to_account VARCHAR(20), IN p_amount DECIMAL(15,2), IN p_transaction_ref VARCHAR(50), OUT p_result VARCHAR(100) ) BEGIN DECLARE v_from_balance DECIMAL(15,2) DEFAULT 0; DECLARE v_to_balance DECIMAL(15,2) DEFAULT 0; DECLARE v_min_balance DECIMAL(10,2) DEFAULT 0; DECLARE v_daily_limit DECIMAL(12,2) DEFAULT 0; DECLARE v_daily_used DECIMAL(15,2) DEFAULT 0; DECLARE v_from_status VARCHAR(20) DEFAULT ''; DECLARE v_to_status VARCHAR(20) DEFAULT ''; DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN -- Atomicity: Any error aana complete rollback ROLLBACK; SET p_result = 'Transaction failed due to system error'; INSERT INTO transaction_log (transaction_ref, from_account, to_account, amount, status, failure_reason) VALUES (p_transaction_ref, p_from_account, p_to_account, p_amount, 'FAILED', 'System error occurred'); END; -- Start transaction for Atomicity START TRANSACTION; -- Set isolation level for consistency SET TRANSACTION ISOLATION LEVEL READ COMMITTED; -- Validate input parameters IF p_amount <= 0 THEN SET p_result = 'Invalid amount: Amount must be positive'; ROLLBACK; LEAVE; END IF; -- Check if accounts exist and are active (Consistency) SELECT balance, min_balance, daily_limit, status INTO v_from_balance, v_min_balance, v_daily_limit, v_from_status FROM bank_accounts WHERE account_number = p_from_account FOR UPDATE; IF v_from_status != 'ACTIVE' THEN SET p_result = 'Source account is not active'; ROLLBACK; LEAVE; END IF; SELECT balance, status INTO v_to_balance, v_to_status FROM bank_accounts WHERE account_number = p_to_account FOR UPDATE; IF v_to_status != 'ACTIVE' THEN SET p_result = 'Destination account is not active'; ROLLBACK; LEAVE; END IF; -- Check minimum balance constraint (Consistency) IF (v_from_balance - p_amount) < v_min_balance THEN SET p_result = 'Insufficient balance: Would breach minimum balance requirement'; ROLLBACK; LEAVE; END IF; -- Check daily transaction limit (Business Rule Consistency) SELECT COALESCE(total_debited, 0) INTO v_daily_used FROM daily_transaction_limits WHERE account_number = p_from_account AND transaction_date = CURDATE(); IF (v_daily_used + p_amount) > v_daily_limit THEN SET p_result = 'Daily transaction limit exceeded'; ROLLBACK; LEAVE; END IF; -- All validations passed, execute the transfer (Atomicity) -- Debit from source account UPDATE bank_accounts SET balance = balance - p_amount WHERE account_number = p_from_account; -- Credit to destination account UPDATE bank_accounts SET balance = balance + p_amount WHERE account_number = p_to_account; -- Update daily transaction tracking INSERT INTO daily_transaction_limits (account_number, transaction_date, total_debited, transaction_count) VALUES (p_from_account, CURDATE(), p_amount, 1) ON DUPLICATE KEY UPDATE total_debited = total_debited + p_amount, transaction_count = transaction_count + 1; -- Create transaction log entries for audit trail INSERT INTO transaction_log (transaction_ref, from_account, to_account, transaction_type, amount, balance_before, balance_after, status) VALUES (p_transaction_ref, p_from_account, p_to_account, 'TRANSFER', p_amount, v_from_balance, v_from_balance - p_amount, 'SUCCESS'), (CONCAT(p_transaction_ref, '_CREDIT'), p_to_account, p_from_account, 'DEPOSIT', p_amount, v_to_balance, v_to_balance + p_amount, 'SUCCESS'); -- Commit transaction for Durability COMMIT; SET p_result = 'Transaction completed successfully'; END // DELIMITER ;

Atomicity: EXIT HANDLER use panni any error la complete rollback
Consistency: All business rules, constraints validate pannurom
Isolation: FOR UPDATE locks use panni concurrent access control
Durability: COMMIT successful aana data permanent ah save aagum
Complete Validation: Amount, account status, limits ellaam check pannurom

ACID Violations and Prevention

Common ACID Violations:

1. Atomicity Violation - Partial Transaction
-- Wrong way - No transaction boundary UPDATE accounts SET balance = balance - 5000 WHERE id = 1; -- If system crashes here, money debited but not credited UPDATE accounts SET balance = balance + 5000 WHERE id = 2; -- Correct way - Proper transaction boundary START TRANSACTION; UPDATE accounts SET balance = balance - 5000 WHERE id = 1; UPDATE accounts SET balance = balance + 5000 WHERE id = 2; COMMIT;
2. Consistency Violation - Business Rule Breach
-- Wrong way - No validation UPDATE bank_accounts SET balance = -5000 WHERE account_number = 'ACC001'; -- Correct way - Proper validation UPDATE bank_accounts SET balance = balance - 5000 WHERE account_number = 'ACC001' AND balance >= 5000 AND (balance - 5000) >= min_balance;
3. Isolation Violation - Dirty Read
-- Wrong way - Reading uncommitted data SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED; -- This allows dirty reads -- Correct way - Proper isolation level SET TRANSACTION ISOLATION LEVEL READ COMMITTED; -- Or higher based on requirements
4. Durability Violation - No Proper Commit
-- Wrong way - No explicit commit in critical operations START TRANSACTION; UPDATE critical_data SET value = 'important_change'; -- Connection closes without COMMIT - changes lost -- Correct way - Explicit commit START TRANSACTION; UPDATE critical_data SET value = 'important_change'; COMMIT; -- Ensures durability

Best Practices for ACID Compliance

ACID Implementation Best Practices:

1. Transaction Design
  • Keep transactions as short as possible
  • Avoid user interaction inside transactions
  • Use appropriate isolation levels
  • Handle exceptions properly
2. Error Handling
-- Proper error handling pattern DELIMITER // CREATE PROCEDURE SafeTransaction() BEGIN DECLARE EXIT HANDLER FOR SQLEXCEPTION BEGIN ROLLBACK; RESIGNAL; -- Re-throw the error END; START TRANSACTION; -- Your operations here COMMIT; END // DELIMITER ;
3. Performance Optimization
  • Use indexes for frequently accessed columns
  • Minimize lock duration
  • Choose optimal isolation levels
  • Monitor deadlock occurrences
4. Monitoring and Maintenance
  • Enable transaction logging
  • Monitor long-running transactions
  • Regular backup and recovery testing
  • Performance metrics tracking
