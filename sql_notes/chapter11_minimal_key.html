🎯 Key Types Overview

🔑 Minimal Key

Smallest Unique Combination

Minimum columns needed for uniqueness

Property: Cannot remove any column

🔗 Composite Key

Multiple Column Key

Two or more columns combination

Property: All columns needed

⭐ Simple Key

Single Column Key

Only one column for uniqueness

Property: Simplest form

📊 Compound Key

Complex Key Structure

Multiple attributes combined

Property: Business logic based

🔍 Minimal Key Properties

Uniqueness Non-redundancy Minimality Irreducibility Efficiency

-- Student registration table CREATE TABLE student_courses ( student_id INT NOT NULL, course_code VARCHAR(10) NOT NULL, semester VARCHAR(10) NOT NULL, year INT NOT NULL, grade CHAR(2), instructor_name VARCHAR(100) ); -- Sample data insert (using safe, generic data) INSERT INTO student_courses VALUES (101, 'CS001', 'Fall', 2024, 'A', 'Prof_Alpha'), (101, 'CS002', 'Fall', 2024, 'B', 'Prof_Beta'), (101, 'CS001', 'Spring', 2024, 'A', 'Prof_Gamma'), (102, 'CS001', 'Fall', 2024, 'B', 'Prof_Alpha'), (102, 'CS002', 'Spring', 2024, 'A', 'Prof_Delta'), (103, 'CS001', 'Fall', 2024, 'C', 'Prof_Alpha');

🔍 Finding Minimal Key Steps

Step 1: Test Single Columns
student_id: 101 appears 3 times - Not unique
course_code: CS001 appears 3 times - Not unique
semester: Fall appears 4 times - Not unique
year: 2024 appears 6 times - Not unique
Result: No single column is minimal key
Step 2: Test Two Column Combinations
(student_id, course_code): (101, CS001) appears 2 times - Not unique
(student_id, semester): (101, Fall) appears 2 times - Not unique
(course_code, semester): (CS001, Fall) appears 3 times - Not unique
Result: Two columns not enough
Step 3: Test Three Column Combinations
(student_id, course_code, semester): All combinations unique!
(student_id, course_code, year): (101, CS001, 2024) appears 2 times - Not unique
Result: (student_id, course_code, semester) is minimal key
-- Create table with minimal key as primary key CREATE TABLE student_courses_final ( student_id INT NOT NULL, course_code VARCHAR(10) NOT NULL, semester VARCHAR(10) NOT NULL, year INT NOT NULL, grade CHAR(2), instructor_name VARCHAR(100), -- Minimal key as composite primary key PRIMARY KEY (student_id, course_code, semester), -- Additional indexes for better performance INDEX idx_student (student_id), INDEX idx_course (course_code), INDEX idx_semester (semester) );

-- Product inventory table CREATE TABLE product_inventory ( product_code VARCHAR(20) NOT NULL, warehouse_id INT NOT NULL, location_zone VARCHAR(10) NOT NULL, shelf_number INT NOT NULL, quantity INT, last_updated DATE ); -- Sample data (using safe, generic patterns) INSERT INTO product_inventory VALUES ('PROD_A001', 1, 'Zone_A', 101, 50, '2024-01-15'), ('PROD_A001', 2, 'Zone_B', 201, 30, '2024-01-16'), ('PROD_B002', 1, 'Zone_A', 102, 25, '2024-01-17'), ('PROD_A001', 1, 'Zone_C', 301, 40, '2024-01-18'), ('PROD_C003', 2, 'Zone_A', 102, 60, '2024-01-19');

❌ Wrong Key Selection:

Only product_code:
  • Same product multiple warehouses-la irukalam
  • Duplicate entries allow aagum
  • Data integrity problems

✅ Correct Minimal Key:

(product_code, warehouse_id, location_zone):
  • Unique identification possible
  • No redundancy

-- Correct table design with minimal key CREATE TABLE product_inventory_correct ( product_code VARCHAR(20) NOT NULL, warehouse_id INT NOT NULL, location_zone VARCHAR(10) NOT NULL, shelf_number INT NOT NULL, quantity INT DEFAULT 0, last_updated TIMESTAMP DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP, -- Minimal key as primary key PRIMARY KEY (product_code, warehouse_id, location_zone), -- Foreign key reference (if warehouse table exists) -- FOREIGN KEY (warehouse_id) REFERENCES warehouses(warehouse_id), -- Check constraints CONSTRAINT chk_quantity CHECK (quantity >= 0), CONSTRAINT chk_shelf CHECK (shelf_number > 0) );

💡 Example 3: Order Management System

-- Order line items table CREATE TABLE order_line_items ( order_id INT NOT NULL, product_id INT NOT NULL, line_number INT NOT NULL, quantity INT NOT NULL, unit_price DECIMAL(10,2) NOT NULL, discount_percent DECIMAL(5,2) DEFAULT 0, total_amount DECIMAL(10,2) ); -- Sample data INSERT INTO order_line_items VALUES (1001, 2001, 1, 2, 100.00, 5.00, 190.00), (1001, 2002, 2, 1, 150.00, 0.00, 150.00), (1001, 2003, 3, 3, 75.00, 10.00, 202.50), (1002, 2001, 1, 1, 100.00, 0.00, 100.00), (1002, 2004, 2, 2, 200.00, 15.00, 340.00);
Minimal Key Analysis:
Test (order_id): 1001 appears 3 times - Not unique
Test (product_id): 2001 appears 2 times - Not unique
Test (order_id, product_id): All combinations unique - This could work
Test (order_id, line_number): All combinations unique - This could work too
Business Decision: (order_id, line_number) is better because line_number sequence important
-- Final table with chosen minimal key CREATE TABLE order_line_items_final ( order_id INT NOT NULL, product_id INT NOT NULL, line_number INT NOT NULL, quantity INT NOT NULL, unit_price DECIMAL(10,2) NOT NULL, discount_percent DECIMAL(5,2) DEFAULT 0, total_amount DECIMAL(10,2), -- Minimal key as primary key PRIMARY KEY (order_id, line_number), -- Foreign key constraints -- FOREIGN KEY (order_id) REFERENCES orders(order_id), -- FOREIGN KEY (product_id) REFERENCES products(product_id), -- Additional indexes INDEX idx_product (product_id), INDEX idx_order_product (order_id, product_id), -- Check constraints CONSTRAINT chk_quantity CHECK (quantity > 0), CONSTRAINT chk_unit_price CHECK (unit_price > 0), CONSTRAINT chk_discount CHECK (discount_percent >= 0 AND discount_percent <= 100), CONSTRAINT chk_line_number CHECK (line_number > 0) );

🔧 Use Cases

1. Social Media Posts

Table: user_posts
Possible Keys: (user_id, timestamp), (user_id, post_sequence)
Minimal Key: (user_id, post_sequence) - timestamp may have duplicates
Business Logic: User can't post multiple posts with same sequence number

2. Banking Transactions

Table: account_transactions
Possible Keys: (account_id, transaction_date, amount), (transaction_id)
Minimal Key: (transaction_id) - if system generated unique ID
Business Logic: Each transaction has unique system ID

3. Employee Attendance

Table: daily_attendance
Possible Keys: (employee_id, attendance_date), (employee_id, attendance_date, shift)
Minimal Key: (employee_id, attendance_date, shift) - if multiple shifts possible
Business Logic: Employee can work multiple shifts in same day

4. Course Enrollment

Table: student_enrollments
Possible Keys: (student_id, course_id), (student_id, course_id, semester)
Minimal Key: (student_id, course_id, semester) - if same course multiple semesters
Business Logic: Student can take same course in different semesters
